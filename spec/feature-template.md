# Feature — 名称

文件名用 `feature-<short-name>.md`，不带编号前缀。状态行必填。
状态流转 Draft → Accepted → Implementing → Implemented。

**这是设计文档。** 写「这套机制怎么工作、为什么成立、出错了怎样」，不写验证输出、
测试通过数、改动文件清单、实施流水 —— 那些在 git history 与 PR 里。单个 feature 控制在
300 行内。

**金字塔结构：先总后分，从简略到详细。** 「总览」一节就能让读者看懂整套机制；下面每一节
都是它的展开。节内同样先给结论再给论证 —— 不要一上来就抛字段表。

**标题带序号**：`## 1` / `## 2`、节内 `### 2.1` / `### 2.1.1`。编号是给人引用的
（「按 3.2 那条规则」），层级也是一眼可见的。

**总览里要有例子**：一段具体的流转 —— 谁发了什么、产生了几条记录、每条去了哪。读者靠
它确认自己看懂了机制；机制讲得再抽象，例子也给不了，就说明还没想清楚。

状态：Draft

## 1 背景与目标

用户场景、要解决的问题、明确不包含的范围。

## 2 前置依赖

关联 feature、模块、协议版本。

## 3 总览

### 3.1 一句话

一句话说清这个机制承诺什么。

### 3.2 流程

流程图。四条贯穿全文的规则。

### 3.3 一个完整的例子

具体的流转，带上真实的帧与字段值。

## 4 接口与数据

输入/输出、实体字段、身份/权限、幂等、不变量。

## 5 实现方案

模块职责、数据流、状态机、关键算法。

## 6 失败与恢复

超时、重复/乱序、取消、重启、部分成功、外部副作用未知。**已知的缺口也写在这里** ——
那是设计的边界，不要另开一段列限制清单。

## 7 跨仓库协议变更

Hymio / Nostalgia / 客户端要跟着改的字段与取值。

## 8 待决事项

需要后续确认的选型与开放问题。
